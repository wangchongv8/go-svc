# Review 检查清单

本文档用于 Claude Code 每阶段实现后的 review。

## 通用检查

- 变更是否符合当前 phase 范围。
- 是否偏离 `docs/architecture.md`。
- 是否更新 README 或相关文档。
- 是否存在无法运行的命令或过期说明。
- 是否引入未讨论的新依赖。
- 是否存在重复代码或明显过度抽象。
- 是否有基本错误处理。
- 是否有健康检查或最小验证入口。

## Go 工程检查

- `go test ./...` 是否通过。
- `gofmt` 是否已执行。
- 包名、目录名和模块名是否清晰。
- 配置是否避免硬编码敏感信息。
- context、超时和错误返回是否合理。
- 日志是否有基本上下文。

## go-zero 检查

- API、RPC、model 目录是否符合 go-zero 惯例。
- `.api` 和 `.proto` 文件是否清晰。
- 生成代码是否和手写代码边界明确。
- 配置文件是否能区分本地、Compose 和 K8s。
- RPC 调用是否有超时和错误处理。

## Docker 检查

- Dockerfile 是否使用合理的多阶段构建。
- 镜像是否避免包含不必要文件。
- Compose 服务名、端口、网络和健康检查是否清晰。
- 依赖服务启动顺序是否可靠。
- README 是否包含一键启动和清理命令。

## Kubernetes 检查

- Deployment、Service、ConfigMap、Secret 是否分离。
- readinessProbe 和 livenessProbe 是否合理。
- 镜像名、端口和环境变量是否一致。
- 是否提供本地验证方式。
- YAML 是否避免复制粘贴错误。

## 微服务设计检查

- API 层是否只做接入、鉴权、聚合和 DTO 转换。
- RPC 服务是否拥有自己的业务边界。
- 服务间调用链是否清晰。
- 是否避免跨服务直接读写对方数据表。
- 是否考虑幂等、事务边界和失败补偿。

## 可观测性检查

- 日志是否结构化。
- 关键请求是否有 trace id 或 request id。
- 是否暴露指标端点。
- 是否有基本 dashboard 或查询说明。
- 错误日志是否包含足够定位信息。

## Review 输出模板

```text
结论：
- 通过 / 需要修改后再进入下一阶段

高优先级问题：
- 文件:行号 问题描述和建议

中低优先级问题：
- 文件:行号 问题描述和建议

测试和验证：
- 已确认通过的命令
- 未能运行的命令及原因

建议下一步：
- 下一阶段前需要补充或修正的事项
```
